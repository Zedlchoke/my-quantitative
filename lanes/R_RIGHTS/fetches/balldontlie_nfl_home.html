    Authentication

    JavaScript examples use the built-in fetch API (Node.js 18+ or a modern browser). Python examples use requests; install it with python -m pip install requests.

    To authorize, use this code:

    curl "api_endpoint_here" -H "Authorization: YOUR_API_KEY"

    const response = await fetch("https://api.balldontlie.io/nfl/v1/teams", {
  headers: { Authorization: "YOUR_API_KEY" },
});
if (!response.ok) {
  throw new Error(`Request failed: ${response.status}`);
}
const data = await response.json();

    import requests

response = requests.get(
    "https://api.balldontlie.io/nfl/v1/teams",
    headers={"Authorization": "YOUR_API_KEY"},
    timeout=30,
)
response.raise_for_status()
data = response.json()

    Make sure to replace YOUR_API_KEY with your API key.

    BALLDONTLIE uses API keys to allow access to the API. You can obtain an API key by creating a free account at our website

    We expect the API key to be included in all API requests to the server in a header that looks like the following:

    Authorization: YOUR_API_KEY

    You must replace YOUR_API_KEY with your personal API key.
    Trial keys use the same api_key and Authorization header as paid keys. During the trial window, requests are capped at 5 req/min; when the trial converts to paid GOAT or ALL-ACCESS, the key uses the paid 600 req/min limit automatically. No integration change is required when the trial expires or converts.

    Pagination

    This API uses cursor based pagination rather than limit/offset. Endpoints that support pagination will send back responses with a meta key that looks like what is displayed on the right.

    {
  "meta": {
    "next_cursor": 90,
    "per_page": 25
  }
}

    You can use per_page to specify the maximum number of results. It defaults to 25 and doesn't allow values larger than 100.

    You can use next_cursor to get the next page of results. Specify it in the request parameters like this: ?cursor=NEXT_CURSOR.

    Errors

    The API uses the following error codes:

    Error Code Meaning
    401 Unauthorized - You either need an API key or your account tier does not have access to the endpoint.
    400 Bad Request -- The request is invalid. The request parameters are probably incorrect.
    404 Not Found -- The specified resource could not be found.
    406 Not Acceptable -- You requested a format that isn't json.
    429 Too Many Requests -- You're rate limited.
    500 Internal Server Error -- We had a problem with our server. Try again later.
    503 Service Unavailable -- We're temporarily offline for maintenance. Please try again later.

    HTTP Request

    GET https://api.balldontlie.io/nfl/v1/player_designations

    Query Parameters

    Parameter Required Description
    season No Season year. Supply with week.
    week No Week within the selected season phase. Supply with season.
    season_types No Array of season types: 1 = preseason, 2 = regular season, 3 = postseason; for example season_types[]=2&season_types[]=3. Requires season and week; defaults to [2] for an explicit week.
    team_ids[] No Filter by one or more BALLDONTLIE team IDs.
    cursor No Cursor from the preceding response.
    per_page No Page size from 1 to 100; default 25.

    When season, week, and season_types are all omitted, the next unfinished game determines the current season, phase, and week. Canceled and postponed games are excluded from that selection.

    Designation Fields

    Field Meaning
    id Stable designation ID for the player and game.
    season Season year of the game.
    week Week number within the game's season phase.
    season_type Season phase: preseason, regular, or postseason.
    game_id BALLDONTLIE ID of the game.
    player, team Player identity and team for this game, using BALLDONTLIE IDs.
    practice_reports Daily practice participation for this game, with a date (YYYY-MM-DD) and status. did_not_participate means no practice participation, limited means partial participation, and full means full participation. An empty array means no daily reports are available; it does not establish that the player practiced or is healthy.
    injury Reported injury or reason for the player's designation. null means no description is available, not that the player is uninjured.
    game_status Reported availability designation for this game: questionable means participation is uncertain, doubtful means participation is unlikely, and out means the player will not play. null means no game designation is available; it is not confirmation that the player will play.
    active Game-day active status: true means active, false means inactive, and null means not yet known or unavailable. Being active does not guarantee the player will enter the game.
    starter Actual starting status for the completed game: true means the player started, false means the player did not start, and null means not yet known or unavailable. This is not a projected starter.
    did_not_play Participation in the completed game: true means the player did not play, false means the player played, and null means not yet known or unavailable. This does not describe practice participation or establish inactive status.
    updated_at Date and time the designation record was last updated, in ISO 8601 format. This is not necessarily the time an individual status changed.

    Practice participation, game availability, game-day active status, and completed-game participation describe different things. For example, a player can miss practice (did_not_participate) and still play, or practice fully while still having a reported injury. A player can also be active for the game (active: true) but never enter it (did_not_play: true). Do not treat null as false.

    Practice reports and game designations can become available before game day. Active status becomes available with game-day inactive announcements; starter and DNP values describe the completed game. Historical coverage varies by game and field: practice reports and active status may be unavailable even when starter and DNP values are present. Player profile details describe the player; the separate team field supplies the game's team context.

    Daily Fantasy Sports

    Daily Fantasy Sports (DFS) endpoints provide lineup-building data for NFL. These endpoints require GOAT tier.

    A slate is the pool and rule set a user builds a lineup against. Its events are the real games included in that pool, and its roster slots define the lineup positions that must be filled. Draftables are the players or teams a user can select for those slots, with slate-specific positions and salaries.

    A typical client flow is:

    1. List slates for a date or, for NFL, a season and week.
    2. Get one slate to show its included games and roster requirements.
    3. List draftables for that slate to power player selection.

    Slates are not limited to the latest record. Date, week, ID, provider, format, scope, and active-state filters let clients build current and historical views. Contest entries are not part of these endpoints.

    Use draftkings for the providers[] filter to retrieve DraftKings slates.

    Fantasy Football

    The Fantasy Football API provides season projections, weekly lineup projections, completed weekly performance, rankings, ADP, auction values, ownership percentages, and scoring definitions. These endpoints require GOAT tier.

    Scoring is season-specific and intentionally flexible. Use the scoring-formats endpoint to discover the definitions available for a season instead of hard-coding one league structure. Standard, half-PPR, and PPR values can be returned together, and the same envelope can accommodate additional formats.

    Endpoint Purpose
    /nfl/v1/fantasy/scoring_formats Discover scoring keys and their rules.
    /nfl/v1/fantasy/projections Get season projections, or weekly lineup projections when week is supplied.
    /nfl/v1/fantasy/weekly_stats Get regular-season weekly stats and fantasy-point totals.
    /nfl/v1/fantasy/rankings Get overall, positional, auction, and other ranking variants.
    /nfl/v1/fantasy/adp Get ADP, auction, rostered, and started data.
    The player, team, and game objects use the same IDs as the NFL players, teams, and games endpoints. The team object identifies the team for the fantasy record. Team defense/special-teams records have player: null and use the team object.

    Current records return date: null. Where supported, pass date=YYYY-MM-DD to request the exact snapshot collected on that date. An unavailable date returns an empty page; it does not substitute a nearby snapshot. weekly_stats does not accept date.

    weekly_stats covers regular-season weeks 1 through 18 only and does not accept a postseason filter. For postseason data, /nfl/v1/stats includes all season types by default; use /nfl/v1/season_stats with season_types[]=3 for postseason totals. Weekly conversion breakdowns and field-goal-distance fields are not available for postseason; season totals can include total_two_point_convs.

    Weekly fantasy stats update periodically rather than in real time. During the active season, records can change when newer results become available, including while a game is in progress. There is no fixed post-final availability time. collected_at is when the record was collected, not when the game ended; records loaded together for a historical season can share the same value.

    All endpoints use cursor pagination. Array filters require bracket notation, for example player_ids[]=38&positions[]=QB.

    Weekly stats and scoring contract

    Weekly stats are the latest available observations, not a finalized DFS settlement feed. The supplied Standard, Half PPR, and PPR formats are not DraftKings contest rules.

    Identity and missing values. There is at most one current D/ST record per season, week, and team, linked to its game; a row is not guaranteed for every team or game. player is null for D/ST. Corrections update the current record in place rather than creating a revision record. This endpoint does not expose dated revisions.

    stats is a sparse numeric map for both players and D/ST. An explicit zero is a reported numeric value. An absent key contributes zero to the published fantasy-points calculation, but is not a guarantee that the event did not occur or that collection is complete. There is no per-key availability flag to distinguish an omitted zero from an unavailable observation. The season-stat rule about nullable fields does not make weekly key omission equivalent to a reported null. This applies equally to two-point conversions, fumbles_lost, return touchdowns, and offensive_fumble_recovery_touchdowns.

    D/ST counters. D/ST values are team-level fantasy observations, not a sum that clients should reconstruct from player rows. The following names describe the reported categories; they do not guarantee complete coverage of every return role or event:

    Stat keys Reported category
    defensive_sacks, defensive_interceptions, defensive_safeties Sacks, interceptions, and safeties credited to the defense.
    opponent_fumble_recoveries, kicks_blocked Opponent fumbles recovered and blocked kicks.
    interception_return_touchdowns, fumble_return_touchdowns, blocked_kick_return_touchdowns Touchdowns classified by the indicated return type.
    kick_return_touchdowns, punt_return_touchdowns Kickoff and punt return touchdowns.
    two_point_returns, one_point_safeties Conversion returns worth two points and one-point safeties.
    offensive_fumble_recovery_touchdowns Offensive fumble recoveries for touchdowns; not interchangeable with defensive fumble-return touchdowns.

    The API does not provide event identifiers or a guarantee that all touchdown fields are mutually exclusive. A player's return can also be credited to the team's D/ST row; do not add player and team rows to produce a team total. An exhaustive return-role and event-overlap dictionary is not currently available.

    Points and yards allowed. points_allowed is the reported points-allowed counter; dst_points_allowed is a separate reported D/ST points-allowed counter. Their equality in a particular game does not make them aliases. Neither field has a guaranteed DraftKings points-allowed definition. In particular, this endpoint does not specify an inclusion/exclusion contract for offensive scores, interception/fumble return touchdowns against, kickoff/punt return touchdowns against, blocked-kick returns, safeties, extra points, or one- and two-point conversion returns. Do not infer these rules from the final scoreboard or from the dst_ prefix. To reproduce a supplied format, use the stat keys in that format's rules; those may use points_allowed_* rather than dst_points_allowed_*.

    Bucket values are supplied observations, not recomputed by this endpoint from the raw counters. For observed weekly stats they represent range indicators: X_to_Y names inclusive endpoints, under_100 means less than 100, and 550_plus means at least 550. The same naming applies to points_allowed_*, dst_points_allowed_*, and yards_allowed_*. Do not assume a scoring-rule list enumerates every available bucket. For example, points_allowed_18_to_21, points_allowed_22_to_27, and yards_allowed_300_to_349 can be present even when the format has no rule for them. Such ranges contribute no bucket points under that format; this does not imply all buckets in stats are zero.

    Calculating totals. For each rule item, multiply stats[item.stat] (zero if absent) by position_points[position] when that override exists, otherwise by points, then sum the contributions. An override replaces the base value; it does not add to it. For example, points=6 and position_points.DST=6 awards six points per event, not twelve. is_reverse is descriptive rule metadata and does not apply another sign change in this calculation. Negative scoring is expressed by the effective points value.

    Each fantasy_points entry embeds its season-specific scoring format. derived=true indicates a format calculated from another definition; derived Half PPR retains Standard's other rules and scores receptions at 0.5. rules.schema_version versions the rule structure, not the stats dictionary. Totals are calculated from the numeric stats using the associated rules and are stored values, not recalculated when you request the endpoint. There is no atomic revision token covering stats, totals, and rules during an update; compare them again on a subsequent fetch if they temporarily differ.

    For example, Buffalo's 2025 week 1 D/ST row for game 423959 has 2 sacks, 1 opponent fumble recovery, the 35–45 points-allowed bucket, and the 400–449 yards-allowed bucket. The supplied formats score these as 2 + 2 - 3 - 3 = -2.

    Freshness and completeness. collected_at is collection time, not a strictly monotonic sequence or a content revision identifier. Equal timestamps are not a guarantee of identical values. Corrections can appear after the game ends. game.status_state=final describes the game, not completion of the stat population; there is no separate completeness or correction-finality signal. A versioned, exhaustive stats-map data dictionary is not currently exposed.

    Player Props

    Player prop betting data is LIVE and updated in real-time. We do not store historical data.
    As games near completion, many (or all) player props may be removed from sportsbooks.

    The Player Props API provides real-time player prop betting odds for NFL games. Player props allow betting on individual player performances such as passing yards, touchdowns, receptions, and more.

    Market Types

    The API supports two market types:

    • over_under: Traditional over/under markets where users can bet on whether a player will go over or under a specific line value
    • milestone: Milestone markets where users bet on whether a player will reach a specific achievement (e.g., 300+ passing yards)

    This endpoint retrieves player prop betting odds for a specific NFL game. The game_id parameter is required.

    This endpoint returns all player props for the specified game in a single response. Pagination is not supported.

    Response Fields

    Field Description
    id Identifies a prop in the current response. IDs may change when data is refreshed; do not use them as permanent offer identifiers.
    updated_at ISO 8601 time the prop data was last refreshed. It does not necessarily indicate when odds changed or when the sportsbook published them.
    meta.per_page Number of matching props returned. There is no next cursor.

    The API does not provide exact-offer mapping to a sportsbook or guarantee that a returned offer is currently available to bet.

    For the scheduled game time, use the date field from Get a Specific Game with the prop's game_id. Player props do not include a game start time.
